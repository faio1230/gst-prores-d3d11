# 調査と方式比較

確認日：2026-09-22。ProRes RAWは対象外。

## 環境と調査範囲

Windows 11 Pro 10.0.26200、Core i9-12900（24論理CPU）、約64 GiB RAM、RTX 3070 8 GiB、NVIDIA 591.86。VulkanデバイスAPIは1.4.325、loaderは1.4.321。D3D11 feature level 11_0のデバイス作成・描画・Compute Shaderを実機確認した。WMIのAdapterRAMは4 GiB付近で桁あふれするためVRAMの根拠には使わず、nvidia-smiを採用した。

インストール済みGStreamerは1.28.2 MSVC x64。`avdec_prores`、D3D11要素は存在するがVulkanプラグインはない。付属FFmpeg DLLはavcodec-61で、検証SDKのavcodec-62とは別版。PATH先頭のFFmpegはImageMagick付属4.2.3、別途Program FilesのFFmpegは2023年版。検証にはプロジェクト内の **FFmpeg n8.1.3-20260921 LGPL shared** を明示指定した。

根拠：`results/environment.json`、`vulkaninfo.txt`、`nvidia-environment.csv`、`ffmpeg-version.txt`、`gst-avdec-prores.txt`。GPUのWin32 external memory/semaphore、keyed mutex拡張は列挙だけでなく共有R16画像のimport・コピー・D3D11読み戻しで確認した。

## 公開実装の再調査

[FFmpeg公式リリース情報](https://ffmpeg.org/)と[8.1 Changelog](https://github.com/FFmpeg/FFmpeg/blob/n8.1/Changelog)で通常ProResのVulkan実装を確認した。これは固定機能のProResデコードエンジンではなく、compute shaderによる処理である。[Khronosの解説](https://www.khronos.org/blog/video-encoding-and-decoding-with-vulkan-compute-shaders-in-ffmpeg)もこの方式を説明している。

`prores` デコーダーにVulkan hwaccelを指定する。独立した `-c:v prores_vulkan` デコーダーを選ぶ方式ではない。`prores_ks_vulkan` はエンコーダーであり今回の検証には使用しない。[実装](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavcodec/vulkan_prores.c)はスライス処理と逆DCTをGPUへ渡し、圧縮パケット・ヘッダー処理などCPU側の仕事も残る。

[GStreamer Vulkan要素一覧](https://gstreamer.freedesktop.org/documentation/vulkan/index.html)、[1.28リリースノート](https://gstreamer.freedesktop.org/releases/1.28/)、公式GitHubミラーmainのファイル一覧と [gst-libav実装](https://github.com/GStreamer/gstreamer/blob/4f552219bccf68a45190f826876776fbb0fc80af/subprojects/gst-libav/ext/libav/gstavviddec.c)を照合した。調査範囲内では通常ProResのVulkan要素やWindows D3D11統合例を確認できなかった。公開ドキュメント一覧だけでは新しい要素を網羅できないためmainのソース一覧も保存した。

GStreamerの `avdec_prores` は既存のCPU基準に利用する。gst-libavのFFmpeg更新だけでVulkanメモリ・デバイス・同期・D3D11出力が自動的に追加される根拠はない。mainの `gstavviddec.c` にVulkan hwdevice設定経路は確認できなかった。hardware decoderの登録除外だけを根拠にprores自体が除外されるとは解釈しない。

開発中変更はGitLab MR検索とAPIにもアクセスしたが、bot challengeで一覧を取得できなかった。検索エンジンからも該当実装を確認できていない。**未公開・未マージ実装が存在しないという断定はしない。** リリース前にこの調査を再実施する。検索エラーとmainのrevisionは `results/` に保存した。

## 方式の比較

| 方式 | 利点 | 問題・判断 |
|---|---|---|
| 既存GStreamer ProRes GPU要素 | 保守範囲が最小 | 調査範囲では見つからず。見つかれば優先 |
| gst-libavにVulkan hwaccel経路を追加 | GStreamer本体側の再利用 | メモリ交渉・同期まで変更が必要。最初の検証には大きい |
| 外部GstVideoDecoder + libavcodec | FFmpegのデコーダーを再利用、ホストに依存しない | 採用候補。まず本リポジトリの独立計測器で評価 |
| FFmpeg別プロセス + rawvideoパイプ | 構成が簡単 | CPU経由、PTSと資源寿命の伝搬が別途必要。GPU効果を損ねる |
| VulkanからCPUへdownload後D3D11 upload | 互換性基準 | 実測で不利。fallback候補であり高速経路ではない |
| Vulkan画像から共有D3D11画像へGPU copy | FFmpegを改変せずCPU画素転送を回避 | 実装・実測済み。今回2回のGPUコピー、CPU同期待ちあり |
| FFmpegが共有画像へ直接decode | コピー削減余地 | custom frame pool、整数view、external handle、同期の検証が必要。未実装 |
| DX11 Compute Shaderデコーダー | D3D11内で完結、共有API境界を削減 | HQ progressive 422/10bit限定でframe復号、品質、速度、GStreamer出力を実機確認。全ProRes形式・実素材・他GPUは未確認 |

FFmpeg 8.1系の [hwcontext_vulkan.c](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavutil/hwcontext_vulkan.c)に今回そのまま使えるD3D11 map経路は確認できない。したがって `hwmap` を挿すだけで共有できるとは扱わない。

## 形式と素材

実測素材は自作の動くtestsrc2、BT.709 limited、60 fps。422 HQは1920×1080・3840×2160で各180フレーム。4444は1920×1080・60フレーム、横方向のアルファ勾配を持つ。生成時の入力色成分は10 bitであり、4444デコードの12 bit出力はネイティブ12 bit実素材の代替証明にならない。

FFmpegのソースには422/444、10/12 bit、alpha、interlacedの処理がある。しかし今回確認したのは上記のprogressive素材のみ。Proxy/LT/Standard/XQ、interlaced、特殊サイズ、HDR、full range、長尺実写、カメラ別素材は未検証。アルファは選定フレームでCPU/Vulkan一致を確認した範囲に限定する。ストリーム内解像度変更はinterop試作で明示的にエラーにする。

## ビルド・配布

実行SDKはBtbNの固定日付Windows shared build。FFmpeg公式 [download](https://ffmpeg.org/download.html) が案内する配布元の一つであり、FFmpegプロジェクト自身によるWindowsバイナリ配布ではない。固定アーカイブSHA256と、初回latestアーカイブとの実行ファイル/DLL一致を保存した。

比較・検査全体の使用物はMSVC/Windows SDK、固定FFmpeg avformat/avcodec/avutil DLL、Vulkan-Headers、GPUドライバーのVulkan loader、Windows D3D11/DXGI/D3DCompiler、GStreamer SDK。純粋DX11 plugin本体はFFmpeg／Vulkan／D3DCompiler DLLへ依存せず、ビルド時にWindows SDKのfxcでCSOを生成する。Python NumPyは画素検査だけに使う。

今回のFFmpegは `--enable-version3` を含み、同梱LICENSEは **LGPLv3**。ファイル単体のLGPL2.1+表記をSDK全体のライセンスと混同しない。配布する際は実際のconfigure条件・依存物・対応ソース・ライセンス文面・変更内容・再リンク/差し替え条件を [FFmpeg公式ライセンス案内](https://ffmpeg.org/legal.html) と各ライセンスに照らして準備する。DLL同梱だけで条件充足とはしない。今回バイナリや第三者ソースをGitへ含めない。

製品向けには必要なcodec/demuxer/hwaccelに限定したFFmpeg DLLを別途ビルドし、GStreamerのLGPL条件と合わせて配布物を監査する。Vulkan-Headersのライセンス、Windows SDKの再配布条件も区別する。ProResの商標・特許・認証の権利をOSSライセンスから推論しない。本プロジェクト自身の公開ライセンスは未決定で、内部検証から公開配布へ移す段階で決める。
