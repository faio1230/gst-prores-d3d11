# 実素材・色・実表示の検証（2026-09-23）

限定対象はprogressive ProRes 422 HQ、10bit、alphaなし。比較と表示はRTX 3070／GStreamer 1.28.2。CPUの画素基準にはリポジトリ内固定SDK `tools/ffmpeg-n8.1-latest-win64-lgpl-shared-8.1/bin/ffmpeg.exe` を明示使用し、PATH上の旧版は使わない。公開素材のバイナリはコミットしない。

## 素材と画素比較

- [Proton Camera公式のサンプル](https://doc.proton-camera.com/docs/samples/)：Atomos Shogun 7収録、1秒に編集したProRes 422 HQ。SDR/REC709版 `media/reference-proton-rec709-hq.mov`、SHA256 `e873a09632c5eb9c3d2d9902af1dd558e70c14d3a458437160a56d91975f03c4`。1920×1080、50fps、50フレーム、BT.709、yuv422p10le。配布元が明記するカメラ由来素材であり、合成テストパターンではない。
- [DJI Inspire 3公式サンプル](https://www.dji.com/inspire-3/samples)：REC.709版の自然映像 `media/reference-dji-nature-4k24-hq.mov`、SHA256 `e97b74358172a82e6b26173cb2f1feba15c321528d49a534a91fccbeb26a8da8`。3840×2160、24fps、129フレーム、BT.709、yuv422p10le。雪山・海・船を実写したカメラ由来素材であることを先頭画像で確認した。ファイルは配布せず、公式リンクから取得する。
- [slomo.tv公式サンプル](https://slomotv.ru/support/sample-files)：`media/reference-slomo-4k-hq60-complete.mov`、SHA256 `a38508d1ee876c8d19e3d0d141da00d148f0bc3a1f3de8926089d63b30166f98`。3840×2160、59.94fps、120フレームのHQだが映像は渦巻き検査パターン。4K/60の互換・負荷試験には使い、実写の根拠にはしない。

Atomos MOVはouter frameが512 byte境界まで埋められ、ProRes pictureの後ろに最大509 byteのtrailerを持つ。slomo.tv MOVは16-byte整列で、120フレームのtrailerは50～65 byteの全ゼロだった。parserは512-byte整列で512 byte未満、または512 byte未満の全ゼロtrailerだけを許容し、slice表がpicture末尾へ厳密に一致する条件を維持した。従来の10種に未整列非ゼロ／過大trailerを加えた12種の不正入力を拒否する。

全50フレームのDX11 `I422_10LE(memory:D3D11Memory)` を検査目的でdownloadし、固定FFmpeg CPUの`yuv422p10le`と同じplane／10bit sampleで比較した結果は次のとおり。全フレーム・全sampleで最大差1以内。詳細は `results/proton-real-yuv.json`。

先頭フレームのGPU VLD係数も独立CPU参照と完全一致した（1080p 4,177,920個、4K実写 16,588,800個）。両者ともshader error 0、12種のparser異常を拒否した。詳細は `results/proton-real-coeff.json` と `results/dji-real-4k-coeff.json`。

| plane | 最大絶対差 | MAE | PSNR dB |
|---|---:|---:|---:|
| Y | 1 | 0.03883 | 74.31 |
| U | 1 | 0.03344 | 74.95 |
| V | 1 | 0.03302 | 75.01 |

DJIの4K実写129フレームも同条件で全画素比較し、Y/U/Vすべて最大差1。MAEは0.03752/0.02891/0.03345、PSNRは74.45/75.59/74.95 dB。詳細は `results/dji-real-4k-yuv.json`。これは1080pのAtomosとは別のカメラ・記録経路である。

slomo.tv MOVはcontainerの3840×2160に対し、clean-aperture side dataが1888×1062へのcropを指定する。固定FFmpegは通常これを自動適用するが、GStreamerの復号出力はcoded full rasterなので、比較器では `-apply_cropping 0` を明示して解像度を揃える。cropを無視して比較することはしない。
検査パターン120フレームのfull raster Y/U/Vも最大差1で完走した（`results/slomo-4k-pattern-yuv.json`）。これは高周波・16-byteゼロtrailerの互換性検査であり、実写検証数には加えない。

当初は3フレーム目以降、先頭2フレームが交互に再読出しされた。原因はUAV書込み後に再利用`GstD3D11Memory`のstaging copyを無効化していなかったこと。`GST_D3D11_MEMORY_TRANSFER_NEED_DOWNLOAD`を3面へ設定後、全50フレームで最大差1へ復帰した。単一フレーム検査では検出できないため、`scripts/compare-d3d11-real.py`で全フレーム比較する。

RGB10A2は同一DX11復号出力からGPU `d3d11convert` とCPU `videoconvert` に分岐させる。両者の入力はBT.709 limited、出力はfull-range RGB10A2。CPU側は`colorimetry=bt709,chroma-site=jpeg`（水平方向中央）と`dither=none`を明示した。CPU既定の左寄せクロマとGPUの中央補間を混ぜると先頭フレームでR/G/B最大39/12/46まで広がる。位置を揃えた50フレーム比較は以下。詳細は `results/proton-real-rgb.json`。

比較器のRGB出力capsも `colorimetry=1:1:5:1`（full-range RGB、BT.709伝達特性・原色）へ固定し、CPU `videoconvert` は `matrix-mode=full,gamma-mode=none,primaries-mode=none` を明示した。1080p全50枚とDJI 4K全129枚を再測定し、各チャンネルの最大差・差分sample数・MAE・符号付き平均・PSNRは固定前と**完全に同じ**だった。記録は `results/proton-real-rgb-explicit.json` と `results/dji-real-4k-rgb-explicit.json`。従って未固定の出力capsだけが系統差の原因ではない。

このMOVのffprobe `chroma_location` は `unspecified`。中央配置はGPU変換との比較条件であって、カメラ収録の物理的クロマ位置が正しいと確定する情報ではない。従ってこの表は変換器間の数値差であり、表示色の規格適合判定ではない。

| channel | 最大絶対差 | MAE | 符号付き平均（CPU−GPU） | PSNR dB |
|---|---:|---:|---:|---:|
| R | 5 | 3.08898 | +3.08898 | 50.10 |
| G | 2 | 0.36595 | −0.2042 | 63.74 |
| B | 5 | 3.06833 | +3.06833 | 50.11 |
| A | 0 | 0 | 0 | 完全一致 |

`scripts/check-bt709.py`で先頭フレームを明示BT.709 limited→full式とも照合した。CPU/GPUの残差は主にR/B約3 code valueの系統差で、同一変換器での完全一致を意味しない。RGBの採用許容値はまだ合意しておらず、「色精度合格」とはしていない。

DJIの4K実写129フレームでは、同じ明示条件のCPU比でR/G/B/A最大差6/2/5/0、MAE 2.2016/0.8488/2.5558/0、符号付き平均（CPU−GPU）+2.2016/−0.8464/+2.5558/0。詳細は `results/dji-real-4k-rgb.json`。こちらも`chroma_location=unspecified`なので、実際のクロマ位置の規格適合までは断定しない。

### 中性グレーでのrange・行列の切り分け

固定SDKの `prores_ks` でblack / gray / whiteの横3帯（384×128、HQ 1枚）を作り、ProResヘッダーとMOVへBT.709メタデータを入れた。ソースは生成物 `build/rgb-neutral-hq.mov` のみで、実素材の件数には含めない。DX11のI422と固定FFmpeg CPUのY/U/Vは全sampleで**完全一致**（`results/rgb-neutral-yuv.json`）。各帯の内側を測ると以下の値となった（`results/rgb-neutral-diagnostic.json`）。中央帯の期待値は `(504−64)×1023/876` を最近接整数にした514で、Cb/Cr=512のためR/G/B共通となる。

| Y/U/V | 独立BT.709期待RGB | CPU `videoconvert` RGB | GPU `d3d11convert` RGB |
|---|---|---|---|
| 64/512/512 | 0/0/0 | 1/0/1 | 0/0/0 |
| 504/512/512 | 514/514/514 | 515/513/515 | 512/514/512 |
| 940/512/512 | 1023/1023/1023 | 1023/1023/1023 | 1021/1022/1021 |

[GStreamer 1.28.2の10bit平面サンプラ](https://github.com/GStreamer/gstreamer/blob/1.28.2/subprojects/gst-plugins-bad/gst-libs/gst/d3dshader/converter-hlsl/PSMain_converter.hlsl) はR16_UNORMの10bit値を64倍して正規化する。一方、[同版のYUV→RGB行列](https://github.com/GStreamer/gstreamer/blob/1.28.2/subprojects/gst-plugins-bad/gst-libs/gst/d3d11/gstd3d11format.cpp) は10bitの最大値1023を基準に係数を組む。したがって低10bitをR16_UNORMに置いた入力では、GPUが行列に渡す値 `code×64/65535` と理想の `code/1023` が一致しない。この量子化スケール差は白が1023に達しない観測と整合する。CPU経路にも灰色の±1丸め差があるため、実写の全誤差をこの1要因だけに帰属させない。

中性帯はクロマ補間の影響を除けるため、独立した式への許容差を「10bit最終丸めの1 code value以内」と置ける。GPUの中間・白R/Bは2 code value不足し、この厳密基準を満たさない。実写ではクロマ位置が未指定で補間差も含まれるため、max 5～6を安易に採用許容値へ格上げしない。現行 `d3d11convert` によるRGBは、画質測定値は揃ったが色精度の採用判定は保留する。

再現手順（固定SDKを明示指定）：

```powershell
& 'tools/ffmpeg-n8.1-latest-win64-lgpl-shared-8.1/bin/ffmpeg.exe' -hide_banner -loglevel error -f lavfi -i 'color=c=black:s=128x128:r=1' -f lavfi -i 'color=c=gray:s=128x128:r=1' -f lavfi -i 'color=c=white:s=128x128:r=1' -filter_complex '[0:v][1:v][2:v]hstack=inputs=3,format=yuv422p10le,setparams=range=tv:color_primaries=bt709:color_trc=bt709:colorspace=bt709[v]' -map '[v]' -frames:v 1 -c:v prores_ks -profile:v 3 -pix_fmt yuv422p10le -movflags +write_colr -y build/rgb-neutral-hq.mov
python scripts/compare-d3d11-real.py build/rgb-neutral-hq.mov --mode yuv --out results/rgb-neutral-yuv.json

```

### DX11専用RGB変換の切り分け（検証用）

標準 `d3d11convert` の正規化差を切り分けるため、`src/prores_rgb.hlsl` のSM5 Compute Shaderを追加した。GStreamerのDX11デコーダーが出す3面R16_UNORM I422から10bit整数コードを復元し、`chroma-site=jpeg` 相当の水平中央補間、BT.709 limited YUV→full RGBを計算し、同一D3D11 device上のRGB10A2 typed UAVテクスチャへ書く。RTX 3070ではこのUAV形式を作成できた。`tests/d3d11_rgb_probe.cpp` は各フレームのD3D11Memory・色メタデータ・寸法・deviceを検査し、最後にstagingへ読み戻す。読み戻しは検証器だけで行い、通常の復号経路には加えない。CPU/Vulkanへの復号fallbackはない。

中性3帯のRGBは黒 `0/0/0`、灰 `514/514/514`、白 `1023/1023/1023` で、独立BT.709式と一致した（`results/rgb-neutral-native-dx11.json`）。`scripts/check-bt709.py` の左端クロマ補間は、clamp後のindexに1を足していた誤りを修正し、境界外の隣接2点をそれぞれclampするようにした。実写ではDX11復号I422を別途downloadした整数コードにPythonのfloat32 BT.709式を適用し、GPU出力の全画素と比較した。符号付き差は基準−GPU。許容差1 codeは10bit最終丸めとGPU/CPU浮動小数演算の差に限定し、実際の各色チャンネル最大差はすべて1だった。

| 素材と比較基準 | 枚数 | R/G/B/A最大差 | R/G/B MAE |
|---|---:|---:|---:|
| Proton 1080p、独立BT.709式−DX11専用RGB | 50 | 1/1/1/0 | 0.0310/0.0304/0.0320 |
| DJI 4K、独立BT.709式−DX11専用RGB | 129 | 1/1/1/0 | 0.0311/0.0311/0.0313 |
| Proton 1080p、GStreamer CPU `videoconvert`−DX11専用RGB | 50 | 3/2/2/0 | 1.7154/0.6147/1.5739 |
| DJI 4K、GStreamer CPU `videoconvert`−DX11専用RGB | 129 | 4/2/3/0 | 1.2007/0.9600/1.3209 |

全フレームの差分sample数、符号付き平均、PSNR、実行コマンドは `results/proton-real-rgb-native-formula.json`、`results/dji-real-4k-rgb-native-formula.json`、`results/proton-real-rgb-native.json`、`results/dji-real-4k-rgb-native.json` に保存した。数式比較は同じDX11復号I422から始めるためRGB変換だけを隔離する。固定SDK CPU復号とのYUV比較は別の全フレーム検査で各面最大1を確認済み。CPU `videoconvert` 自身にも丸めと行列実装の差があり、カメラ素材の `chroma_location` は未指定である。したがって「独立式と1以内」は明示した中央クロマ・BT.709条件での数値的検証であり、撮影時の色意図や表示機器の色管理まで証明しない。またこの専用RGBテクスチャはまだGStreamer `D3D11Memory` に包装・出力しておらず、標準 `d3d11convert` の表示経路は旧来の色差を持つ。

## 実表示とデコーダー単体の分離

`scripts/benchmark-d3d11-display.py`はDX11復号→D3D11 RGB10A2→`d3d11videosink sync=true`を実ウィンドウ／swapchainへ接続し、`present`信号、sinkのrendered/dropped、QoS、CPU、メモリ、nvidia-smiを保存する。WMI報告の現在のディスプレイ設定は3840×2160／60Hz。`present`信号はswapchainへのpresent要求前の時刻であり、物理パネルの発光時刻ではない。各周の最初30件をinterval統計から除外する。seek時にsink統計がリセットされるので周ごとに記録・合算する。

合成60fps素材を3試行×3周×180フレーム表示した結果。p95/p99、seek、CPU/GPU/メモリは3試行の中央値。GPU使用率・VRAMは他プロセスを含むGPU全体値。原データは `results/d3d11-display/`。

| 素材 | 表示/予定 | drop（試行別） | present p95/p99 ms | seek先頭 p95 ms | CPU全体 % | GPU平均 % | peak WS MiB |
|---|---:|---|---:|---:|---:|---:|---:|
| 1080p60 | 540/540 ×3 | 0, 0, 0 | 17.72 / 18.17 | 4.74 | 1.26 | 17.68 | 60.90 |
| 4K60 | 540/540、525/540、540/540 | 0, 14, 0 | 17.80 / 18.37 | 10.48 | 1.98 | 27.30 | 102.82 |

4Kの1試行2周目にはpresent間隔262.7msの単発停止、QoS 15件、drop 14件が生じた。表示p99は残ったpresentだけの統計なので、この停止を表現しない。最大intervalとdropを併記し、安定60fpsの条件は未達として追加反復する。1080pの実写50fpsは3周・150/150表示、drop 0、present p99 21.46ms。

この後の4K追加6試行×540フレーム（`results/d3d11-display-extra/`）は全てdrop 0で、単発停止は再現しなかった。合計9試行中1試行の異常として残し、原因未特定のまま「必ずdrop 0」とは記載しない。

計測器に圧縮入力・DX11デコーダー出力・D3D11 RGB変換出力のPTSと時刻を追加し、合成4K60でさらに12試行×3周×180枚を実行した。結果は予定6480枚、表示6478枚、sink申告drop 0、QoS 2件。12試行中2試行で各1枚が圧縮入力にはあり、デコーダー出力とRGB出力にはなかった（PTSは3周目1.550秒、2周目1.683秒）。欠落直前の圧縮入力→デコーダー出力に22.44/23.28msを要した。`sink dropped=0`はend-to-end無欠落を保証しない。今回の中央値present p95/p99は17.80/18.32ms、最大間隔25.58ms。元の263ms停止は再現せず、根本原因は未特定。時系列と試行別集計は `results/d3d11-display-stages-repeat/` と `results/d3d11-display-stages-repeat-summary.json`。段階別ログはpad probeによるCPU到達時刻で、GPU完了時刻ではない。

同じ計測器で実素材と1080p60も各3試行測り直した。以下のCPUはマシン全体換算のプロセスCPU、GPUは他プロセス込みのデバイス全体サンプリング、WSは当該プロセスpeak working set。p95/p99、seek、CPU/GPU/WSは試行中央値だが、最大present間隔は全試行の最大値。PTS段階ログから算出した全経路の表示枚数を基準とする。

| 素材・条件 | 表示/予定 | sink drop | present p95/p99 ms | 最大間隔 ms | seek先頭p95 ms | CPU/GPU % | peak WS MiB |
|---|---:|---:|---:|---:|---:|---:|---:|
| 合成1080p60、3試行 | 1620/1620 | 0 | 17.79/18.31 | 18.99 | 3.69 | 1.21/17.19 | 62.50 |
| 合成4K60、12試行 | 6478/6480 | 0 | 17.80/18.32 | 25.58 | 8.40 | 2.05/27.56 | 102.90 |
| Proton実写1080p50、3試行 | 450/450 | 0 | 21.26/21.47 | 21.73 | 4.41 | 1.00/11.24 | 61.26 |
| DJI実写4K24、3試行 | 1159/1161 | 1 | 42.72/43.20 | 111.43 | 13.03 | 1.24/13.33 | 114.61 |
| slomo検査パターン4K59.94、3試行 | 1080/1080 | 0 | 17.77/18.18 | 18.69 | 8.60 | 2.18/27.13 | 109.92 |

DJIの欠落試行では初周のPTS 0.125秒が圧縮入力後に消え、さらにsinkが1枚をdropした。正常試行の最初のpresentは約126ms、欠落試行は約362msで、その直後のpresent間隔は111ms。段階ログでは初周0→0.0417秒の圧縮入力が263ms空き、デコーダー出力→RGB出力も一度86.7msかかった。別のDJI追加6試行でも1試行で同じ初周PTS 0.125秒が欠け、最初のpresentが約362ms、最大間隔110msだった（`results/d3d11-display-dji-repeat-summary.json`）。初期表示・GPU処理の遅延と整合するが、ドライバー／OS／要素の責任分界は未確定。

PAUSED preroll後にPLAYINGへ遷移する9試行でも1試行で2枚欠け、最大present間隔112msだった（`results/d3d11-display-dji-preroll-repeat-summary.json`）。prerollだけでは対策にならない。診断用にsinkのQoSを無効化し `max-lateness=-1` としたDJIの9試行では3483/3483枚を表示したものの、最大間隔101msが残った（`results/d3d11-display-dji-lossless-repeat-summary.json`）。これは欠落防止と引き換えに停止が見える条件で、滑らかな表示の合格ではない。同設定の合成4K60は6試行3240/3240枚、最大間隔19.61msだったが、通常設定での稀な停止を否定する試行数ではない。

```powershell
python scripts/benchmark-d3d11-display.py media/synthetic-2160p60-hq.mov --loops 3 --repeats 12 --out results/d3d11-display-stages-repeat
python scripts/summarize-d3d11-display.py results/d3d11-display-stages-repeat --out results/d3d11-display-stages-repeat-summary.json
python scripts/benchmark-d3d11-display.py media/reference-dji-nature-4k24-hq.mov --loops 3 --repeats 9 --preroll --out results/d3d11-display-dji-preroll-repeat
```
