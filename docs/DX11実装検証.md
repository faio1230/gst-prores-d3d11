# DX11でデコーダーを実装できるか

**プロジェクトの最終目標は、純粋なDX11でのGPU復号とGPUメモリのままのGStreamer出力を両立すること。** 本文の基礎検証はその途中段階であり、DX11実装は任意の追加機能ではない。実装順序・到達条件は[開発計画](プラグイン化計画.md)に従う。

判定：**progressive ProRes 422 HQ / 10bitの限定範囲で、SM5復号からGStreamer D3D11Memory直接出力まで成立した。** Vulkan経路とは独立したD3D11デバイス／HLSLだけで実行する。合成素材の長時間・複数instanceに加え、公開カメラ由来1080pの全50フレームと4Kの全129フレームをCPUと最大差1で照合した。実表示4Kにはdrop事例があり、RGB許容値・他GPUを含む採用判定は未完了。新しい結果は[実素材と表示検証](実素材と表示検証.md)。

## 2026-09-22 DX11単一フレーム復号

`src/prores_parser.cpp`、`prores_vld.hlsl`、`prores_idct.hlsl` と `tests/prores_dx11_coeff.cpp` を追加した。CPUはフレーム／picture／slice／plane境界、対象形式、量子化行列を検査し、圧縮planeと処理記述だけをGPUへ転送する。CPU参照VLCは品質検査専用で、通常復号経路の代替ではない。

DX11は次の2 dispatchで処理する。

1. slice×Y/U/Vの1 jobごとにGolomb-Rice/exp-Golomb、DC差分、AC run/level、符号、progressive逆スキャンを実行し、係数bufferへ書く。
2. 8×8 blockごとに逆量子化と2段の分離逆DCTを行い、丸め・0〜1023 clip後にY/U/VのUAVへ直接書く。単体検査は `R16_UINT`、GStreamer出力は `R16_UNORM` を使う。

RTX 3070で合成HQの先頭フレームを検査した結果は次のとおり。コマンドは `./scripts/test-dx11.ps1`、原記録は `results/dx11-decode-*.json`。

| 解像度 | slice | 比較係数 | 係数不一致 | CPU画素との差 | 結果 |
|---|---:|---:|---:|---:|---|
| 1920×1080 | 1,020 | 4,177,920 | 0 | 最大1、MAE Y/U/V=0.002890/0.002664/0.002350 | 合格 |
| 3840×2160 | 4,050 | 16,588,800 | 0 | 最大1、MAE Y/U/V=0.003191/0.002180/0.002035 | 合格 |

画素差1は、DX11のfloat分離IDCTとFFmpeg CPUの整数／固定小数点IDCTが最終丸め境界で異なる場合に限られ、係数、min/max、先頭画素は一致した。現在の明示許容差は10bit code valueで1。これを超える差は不合格とする。既存Vulkan経路で観測した最大17〜31の差をこの許容差で正当化しない。

通常GPU経路の画像コピーは0回で、IDCT shaderが出力textureへ直接書く。CPU読み戻しは検査器だけが行う。GStreamer 1.28.2のpoolでは `I422_10LE(memory:D3D11Memory)` をY=1920×1080、U/V=960×1080の3枚 `DXGI_FORMAT_R16_UNORM`（全てSRV|UAV）として確保し、10bit値を16bit容器の下位bitに保持するため `value / 65535` を書く。`d3d11download` 後の全4,147,200 sampleをCPU参照と比較して最大差1、MAE 0.002699だった。

不正signature、frame size、4444、interlace、alpha、picture/slice/plane size、未参照picture末尾、caps寸法不一致の10ケースはCPU parserで拒否した。2026-09-23にAtomosの512-byte整列trailerと短い全ゼロtrailerへ対応し、未整列非ゼロ／過大trailer拒否を加えた12ケースへ更新した。実素材1080p/4Kは全フレーム確認済み、他GPUベンダーは未確認。

2026-09-24、固定SDKで取り出した合成1080p/4Kと公開実写1080p/4Kの先頭packetに決定的な変異を加え、MSVC AddressSanitizer付きCPU parserを検査した。初回にAC runの末尾等号を通す境界式から`kProgressiveScan[64]`のglobal-buffer-overflowを検出。同じ式をCPU参照とSM5 VLDの両方で修正した。4素材×500変異の再検査は計2,000ケース完走し、構造受理1,430件のうち296件をCPU entropyで検査、係数面末尾到達9件を拒否。合成1080p先頭packetのoffset 7690を`0x14→0x04`とする単一バイト再現例では、CPUの境界エラーとGPU同一jobの`STREAM/DECODE`を確認した。合成1080p/4Kの係数完全一致・画素最大差1、EOS/seek/RGBと公開素材779枚のD3D11Memory/EOSも通過。再現手順は`scripts/test-d3d11-parser-mutations.ps1 -Iterations 500`、集計は`results/verification-parser-mutation-2026-09-24/summary.json`と`results/verification-ac-boundary-2026-09-24/`。これは限定した決定的変異とCPU ASanの結果であり、全bitstream、GPU memory安全性、他GPUの網羅的な保証ではない。

## GStreamer連続出力

`gstproresd3d11.dll` の `proresd3d11dec` は `GstVideoDecoder` 派生で、入力をHQ・progressive・422・10bit・alphaなしに限定する。CPUはframe/picture/slice境界とjob記述を作るだけで、画像のCPUデコードやfallbackはない。圧縮packet、job、係数bufferをフレーム形状ごとに再利用し、32-bit bit windowでVLDを行う。IDCTはpoolから得た3面のD3D11Memoryへ直接dispatchする。

RTX 3070の正式反復中央値では、D3D11Memory供給が1080p 293.8 fps、4K 133.1 fps。検査用 `d3d11download` でGPU完了を含めると255.7/102.2 fps、p99 4.49/11.63 ms。ビルド時CSO化後の初回bufferはD3D11Memory直結で229/232 ms。GPU完了待ちのない直結値とdownload値を区別する。実際の合成・表示は別途測る。

2026-09-24に診断専用の `PRORES_DX11_GPU_TIMING=1` を追加。VLDと逆DCTの各dispatch直前・直後にD3D11 timestampを置き、フレーム単位のdisjoint queryで時刻の信頼性を確認する。[Microsoftのtimestamp/disjoint仕様](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ns-d3d11-d3d11_query_data_timestamp_disjoint)に従い、不連続な測定は失敗扱いとする。`./scripts/measure-d3d11-gpu-stages.ps1 -IncludeReal -GpuLabel 'NVIDIA GeForce RTX 3070'` で3試行、各試行先頭5枚を除いた結果は以下。フレーム件数は素材ごとの予定値と一致、PTS重複なし、disjoint 0。素材SHA256、p95、最大値は `results/gpu-stage-timing-2026-09-24.json`。長い生ログは非コミットの `build/vs18/gpu-stage-timing-logs/` に保存する。

| 素材 | 測定枚数 | VLD 中央値 / p99 | 逆DCT 中央値 / p99 | 両shader合計 中央値 / p99 |
|---|---:|---:|---:|---:|
| 合成1080p60 HQ | 525 | 1.995 / 2.403 ms | 0.305 / 0.326 ms | 2.297 / 2.703 ms |
| 合成4K60 HQ | 525 | 2.226 / 2.586 ms | 1.058 / 1.199 ms | 3.285 / 3.677 ms |
| DJI公開実写4K60 HQ | 1,425 | 2.588 / 2.993 ms | 1.058 / 1.195 ms | 3.647 / 4.099 ms |

この数値はshaderのGPU区間だけで、packet転送、job更新、VLDエラーフラグのreadback、GStreamer割当、表示は含まない。診断モードは毎フレーム逆DCT完了まで明示的に待つため、通常モードのfpsや表示間隔へ流用しない。計測を無効にした通常経路のEOS・seek・動的色/解像度caps・RGBと、DX11係数／画素比較も再通過した（`results/verification-gpu-stage-timing-2026-09-24/`、`results/verification-gpu-stage-core-2026-09-24/`）。

`d3d11_plugin_smoke` では1080p 180フレーム×3回のEOS/NULL再起動、4位置×3フレームのaccurate flushing seek、色メタデータ2ケース、stopとpipeline破棄後の出力buffer保持、明示共有した同一GstD3D11Device上の2instance、破損／未対応／存在しないadapter・fileのエラーを検査した。2026-09-24には同一appsrc pipelineでHQ 1080p→4K→1080pのcapsを2回変更し、各出力のPTS・3面D3D11Memory・テクスチャ寸法、切替前後の1080p全画素一致、先頭bufferの保持寿命を確認した（`results/verification-dynamic-caps-2026-09-24/`）。同日の追加検査で、色のみBT.709→BT.601→BT.709の2回変更でも出力colorimetry・3面D3D11Memory・保持bufferが一致し、BT.601をBT.709専用RGB要素へ渡すとエラー終了した（`results/verification-dynamic-color-2026-09-24/`）。非対応プロファイルへの動的変更と実際のdevice lostは未検証。DLLの直接依存にはGStreamer D3D11とMSVC/Windows runtimeだけが現れ、FFmpeg/Vulkan/D3DCompiler DLLはない。HLSLはビルド時にCSO化してDLL隣へ配置し、作業ディレクトリ外からもロードできる。

4K `dx11-download` を同じpipelineで30分反復し、182,520フレーム、1,014周、wall 1,801.18秒を完走した。定常101.38 fps、p99 11.42 ms、peak WS 172.17 MiB、終了時private 280.02 MiBで、短時間4K試験の約280 MiBから増加していない。独立deviceの2プロセス同時4Kも各91.08/91.86 fpsで成功した。

GStreamer下流は `d3d11convert ! RGB10A2_LE(memory:D3D11Memory)` を1080p/4Kで完走し、検査用download込みのwall値は152.6/68.0 fps。さらに2本の1080p decode/convertを `d3d11compositor` へ入れ、RGB10A2 D3D11Memoryを118.4 fpsで180フレーム合成した。2026-09-23には公開1080p実写50フレームのRGB10A2をBT.709・中央クロマCPU経路と比較し、R/G/B最大差5/2/5を得た。実表示60fpsは4K試行中に14 dropが1回あり、安定合格ではない。convert/compositor内部のrender/copy回数は未測定で、最終downloadは検査用CPU読み戻しである。

FFmpeg CPU/Vulkan比較の実施後に、DX11の基礎検証を追加した。デコーダー自作や移植を性能比較より先に始めていない。

## 実機で実行した内容

`src/dx11_primitives.cpp` / `.hlsl` をMSVCとD3DCompilerの `cs_5_0` でコンパイルし、RTX 3070のD3D11 feature level 11_0でDispatchした。

- ByteAddressBufferから任意ビット位置を読む8,192ケース（32 bit境界をまたぐものを含む）：CPU参照と全件一致。
- 8×8逆DCT：64個の基底入力と64個の擬似ランダム係数ブロックを倍精度CPUの数式と比較。最大誤差0.003902、平均絶対誤差0.000210。
- groupsharedとGroupMemoryBarrierWithGroupSyncを使う2段の分離変換。
- R16_UINT typed UAVの対応フラグを確認。

結果は `results/dx11-primitives.json`。この基礎試験の許容差0.02は浮動小数値用であり、上記の実ProRes画素検査には流用していない。

## Vulkanからの置き換え

| Vulkan実装で使う表現 | D3D11案 | 確認状態 |
|---|---|---|
| u8/u16格納と物理バッファ参照 | ByteAddressBufferのuint load、mask/shift、32 bitオフセット | VLD全体と係数完全一致を確認 |
| push constants / specialization constants | constant buffer、シェーダーvariant | 合成と基礎テストで利用 |
| 動的な画像配列とnonuniform indexing | Y/U/Vへ固定UAVを割当、block別Dispatch | 3面D3D11Memoryへ実装済み |
| 共有メモリとbarrier | groupshared、GroupMemoryBarrierWithGroupSync | 実機確認 |
| VLD後のIDCTパス | UAVを解除し、別パスのSRVへ切替 | 実フレームと連続復号で確認 |
| Vk timeline、external memory | 同じD3D11 immediate contextの順序とGStreamer device共有 | EOS/seek/寿命試験まで確認 |

共通GLSLヘッダーの64 bit型宣言を「全ての算術にネイティブ64 bit整数が必須」とは解釈しない。GPUアドレスを32 bitオフセットへ置き換えられる範囲を定め、4 GiB境界を超えるパケットを拒否する設計が候補。SM5には標準のwave/subgroup命令がなく、必要な協調処理は共有メモリへ置き換える。[Microsoft Compute Shader資料](https://learn.microsoft.com/en-us/windows/win32/direct3d11/direct3d-11-advanced-stages-compute-shader)の1024 threads/group、8 UAV等の上限内に収める。今回の基礎テストは64 threads/group。

## 完全デコーダーへ進める順序

1. 完了：progressive 422 HQ、10 bit、アルファなしに限定したCPU parserと境界検査。
2. 完了：SM5のDC/AC可変長復号、run/level、逆スキャンと全係数照合。
3. 完了（float方式）：逆量子化、逆DCT、10bit丸め／clipとCPU画素比較。整数方式は必要性を性能と許容差から再評価する。
4. 完了：GStreamerの3面R16_UNORM poolへの直書き、連続フレーム、寿命、seek/flush/EOSの基本検査。
5. 完了（合成素材）：4K 30分、起動100回／seek1000回、複数decode、D3D11変換／2入力合成の性能を測った。
6. 次：実素材、RGB色精度、実表示、他GPU、device lostを採用条件に沿って確認する。対象外形式は拡張せず明示エラーを維持する。

FFmpegのshader/parserを翻訳・改変した派生部分はLGPL表示とソース提供を維持し、元revisionと差分を追跡する。HLSLに変換しただけでライセンス条件が消えるわけではない。今回完成とする範囲はHQ progressive 422/10bitであり、全ProRes形式への一般化を主張しない。

採用判断には実際の422素材、必要な同時再生数、画の許容差、複数ベンダーのGPUが必要。ネイティブDX11化を主実装として進め、正確性・同期・GStreamerのD3D11Memory出力を検証する。Vulkan経路の既知問題とDX11経路の検査結果は区別して記録する。
