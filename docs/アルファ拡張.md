# M3：ProResアルファ拡張とAYUV64標準化

2026-09-24、`proresd3d11dec`にアルファ8/16bitのDX11 Compute Shader復号を接続した。パーサが4番目の圧縮面を分離し、GPUでエントロピー復号したアルファと既存Y/U/Vを、GPU内で`AYUV64`の単一`GstD3D11Memory`へ詰める。CPU・FFmpeg・Vulkanへのfallback、および通常経路の画像CPU読み戻しはない。VLD結果の検査用コピーは従来の3枠非同期リングを維持する。アルファなし入力は従来の3面出力のままにする。

GStreamer 1.28.2のD3D11プールは`A444_10LE`などの4面planar形式を受理しないため、アルファ付き出力は`AYUV64`を選んだ。M3採用時点ではGPUの`R16G16B16A16_UNORM`テクスチャ1枚の各成分の下位bitに10/12bit値を入れ、出力capsの`prores-depth`と`prores-chroma-shift`で補っていた。4:2:2のU/Vは隣接画素へ複製した。この旧方式は標準AYUV64の意味と異なるため、後述の「出力の詰め方の変更」で置き換える。両形式は実際にGStreamer D3D11プールでUAV付き単一テクスチャとして確保できた。

検証素材は固定SDKで作った4444系のアルファ付き素材と、対応する422 YUV・444アルファの圧縮面を組み合わせた有効な422+アルファ素材。apco/apcs/apcn/apch/ap4h/ap4x×4:2:2/4:4:4×アルファ8/16bit、計24条件×2枚のCPU・DX11・Vulkan比較で、2,764,800画素のアルファ差0、Y/U/V差最大1。DX11の全Y/U/V係数7,372,800値はCPU参照と完全一致した。RGB変換はDX11出力のAYUV値から独立に計算したBT.709式と最大1（16bitコード）、アルファ差0。元のCPU-YUVとRGBを直接比べると、YUVの最大1コードの差が行列と16bitへの拡大で最大211コードに増幅されるため、RGBAに「CPUとの差1」を流用しない。詳細は`results/m3-alpha-centered-comparison-2026-09-24/summary.json`と`results/m3-alpha-coeff-all-2026-09-24.json`。

## 出力の詰め方の変更（M4後・M5前に採用）

旧M3方式は10/12bit値を16bit成分の下位bitへ入れたため、GStreamer標準のAYUV64を16bit UNORMとして読む`d3d11convert`、`d3d11videosink`、`d3d11download ! videoconvert`では輝度・色・不透明度が本来の約1/16～1/64になった。独自capsの`prores-depth`/`prores-chroma-shift`を標準要素は解釈しない。新方式はY/U/Vを10bitなら`(v << 6) | (v >> 4)`、12bitなら`(v << 4) | (v >> 8)`、alpha8なら`(a << 8) | a`で16bit全域へビット複製し、alpha16は圧縮面から得た16bit値をそのまま保持する。4:2:2のU/Vは**隣接2画素へ複製**して4:4:4へ展開し、補間はしない。AYUV64の出力capsから独自2フィールドを削除し、`proresd3d11rgb`も標準の16bit UNORMとして読み、straight alphaを`RGBA64_LE`へ保持する。alphaなしの`I422_10LE`/`Y444_10LE`/`I422_12LE`/`Y444_12LE`はGStreamer定義どおり下位bit詰めのまま変更しない。

固定SDK FFmpeg n8.1の[`proresdec.c`](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavcodec/proresdec.c)では、alpha16の復号16bit値をyuva444p10へは`>> 6`、yuva444p12へは`>> 4`し、alpha8は10bitへ`(a << 2) | (a >> 6)`、12bitへ`(a << 4) | (a >> 4)`で出力する。よってCPU参照をAYUV64の16bitへ比較するとき、YUVには上記ビット複製、alpha8には元の8bit値の16bit複製を用いる。alpha16はGPUの16bit値をCPU出力深度へ右シフトした値と照合する。FFmpegの10/12bit出力はalpha16の下位6/4bitを保持しないため、そのCPU出力だけではraw16の下位bit一致を証明できない。この限界を含めてalpha差0を判定する。

M3の24交差条件48枚・2,764,800画素とM4のalpha TFF/BFF長尺および可変alpha184枚・1,119,974,400画素では、YUVの元深度換算最大差1、alphaのFFmpeg出力深度での差0。`proresd3d11rgb`のM3全条件RGBAはAYUVから独立計算したBT.709 limited式との差RGB最大1/65535、alpha差0。記録は`results/alpha-standard-m3-24-2026-09-24/summary.json`、`results/alpha-standard-m4-2026-09-24/summary.json`。BT.709の16bit合法範囲としてYの黒4096・白60160、UV中心32768・振幅57344を使用する。

GStreamer 1.28.2の標準2経路、(1) `d3d11convert ! RGBA64_LE(memory:D3D11Memory) ! d3d11download`、(2) `d3d11download ! videoconvert ! RGBA64_LE`を、非不透明のapch/422/10bit/alpha8とap4h/444/12bit/alpha16で全画素検査した。独立BT.709式で固定SDKのCPU-YUVから算出したRGBAとの差は、(1) 最大211/65535、(2) 最大230/65535、alpha差0。許容差は各RGB 256/65535とした。元深度で最大1 codeのDX11/CPU-YUV差が16bit RGBへ約214 codeまで拡大し、`videoconvert`の整数丸め差がAYUV基準で最大85 codeあるためで、実測最大230を覆う。実際のAYUVからの式との差は(1)最大1、(2)最大85。両経路とも標準caps、BT.709、EOSを通過し、alphaは全域に分布した。記録は`results/alpha-standard-converters-2026-09-24/summary.json`。

標準`d3d11videosink`の表示経路は、GStreamer 1.28.2の[`gstd3d11window.cpp`の変換器生成箇所](https://github.com/GStreamer/gstreamer/blob/1.28.2/subprojects/gst-plugins-bad/sys/d3d11/gstd3d11window.cpp#L854)で`GstD3D11Converter`を使用する。`d3d11convert`も同じ変換器を使うため、上記(1)の全画素比較（CPU基準RGB最大211/65535、alpha差0）をsinkの明るさの数値的根拠として採用する。これは画面そのものや表示機器の色管理の検証を意味しない。標準sinkへのAYUV64 D3D11Memoryのnegotiateと20秒の実時間EOSは`results/alpha-standard-display-sink.log`で確認した。スクリーンショットは合格条件に含めず、画面キャプチャを証拠として保存しない。

回帰は新旧M4採用DLLでHQ direct交互4組を測り、1080p 434.35→432.66 fps（−0.39%）、4K 256.56→256.21 fps（−0.13%）で−3%ゲート通過。ASan変異は8素材16,000件通過。alphaなしM1の11素材420枚・M2の18素材780枚はYUV最大1、M2の18素材はD3D11MemoryとRGBのEOS/seek・保持バッファ寿命を通過。公開HQ779枚のD3D11Memory/EOSと、M4 TFF/BFFを含むスモークのEOS・seek・17破損例も通過した。根拠は`results/alpha-standard-hq-ab-2026-09-24/summary.json`、`results/alpha-standard-parser-asan-2026-09-24/summary.json`、`results/alpha-standard-m1-pixels-2026-09-24/summary.json`、`results/alpha-standard-m2-pixels-2026-09-24/summary.json`、`results/alpha-standard-m2-lifecycle-2026-09-24/summary.json`、`results/alpha-standard-hq-public-2026-09-24/summary.json`、`results/alpha-standard-smoke.log`。この追加段階は標準変換・sinkの数値判定と全回帰が通過したため採用し、M5へ進む。最終実表示のQoSと他GPUは別の未達事項として維持する。
