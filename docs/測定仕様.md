# 測定仕様と既知の制限

## 比較条件

CPU/VulkanともFFmpeg n8.1.3の同じ `prores` デコーダーと同じMOVを使用。`thread_count=0`（FFmpegの自動設定）、Vulkan GPU 0、音声なし、最大速度、同一ディスク/OSファイルキャッシュ条件。ファイルキャッシュ・ドライバーのshader cacheを消去しない。プロセス初期化とOS/ドライバーの完全cold startは別である。

本計測器はlibavformatでdemuxする。GStreamer avdec_prores自体との速度比較ではない。GStreamerの時刻同期・下流backpressure・VSyncを含めた表示fpsへ読み替えてはいけない。

## 純粋DX11 GStreamer経路

`d3d11_plugin_bench` はGStreamer pipelineからappsinkへ到着した時刻を記録する。`dx11-direct` はD3D11Memoryをそのまま受け取るためbuffer供給速度であり、各frameのGPU完了待ちはしない。`dx11-download` は `d3d11download` でsystem memoryのI422_10LEへ戻し、GPU完了を含む厳しい比較に使う。通常運用経路にdownloadはない。

`cpu` は同じGStreamer 1.28.2 pipelineの `avdec_prores` とsystem memory I422_10LE。GStreamer内蔵FFmpeg（avcodec-61）であり、固定SDK n8.1.3の `prores_bench` とは別比較である。PATH上のffmpeg.exeは呼ばない。多スレッド固定SDK CPU→D3D11との比較には既存 `cpu-d3d11` を使い、GStreamer CPU値と混同しない。

正式DX11 plugin比較は各素材180フレームを6周、各周先頭30枚を除外、モード順を反転して3プロセス。最終値はビルド時に固定したCSOを使用し、初回値はpipeline生成、device作成、bytecode読込を含む。seek値は周回間の先頭seek 5回と追加4位置の合計9回。CPU%とmemoryの定義、nvidia-smiがGPU全体値である制約は既存計測と同じ。最終DX11値は `results/d3d11-plugin-benchmark-cso/`、同時比較のGStreamer CPU値は `results/d3d11-plugin-benchmark/`。

長時間検査は有限の3秒素材を同一pipelineでflushing seekして反復する。実時間同期はせず最大速度で処理するため、「30分のwall時間」と処理した映像時間を区別する。複数decode検査は同じadapter上の独立プロセス／独立GstD3D11Deviceであり、同一device contextの共有可否は別のsmoke testで確認する。

正式baselineは各素材180フレームを12周、各条件3プロセス。2回目は条件の順序を反転。各周の先頭30フレームを定常統計から除外する。初回試行や他検査と重なった `results/bench/` は探索記録であり、正式判断には `baseline-final/` を使う。失敗した試行を成功値へ混ぜないが、失敗件数とログは残す。

## 時間と統計

- `demux_init_ms`：入力openとstream info検出。
- `device_init_ms`：Vulkan device作成（CPUではほぼ0）。
- `codec_open_ms`：avcodec_open2のみ。遅延初期化・shader処理は初回フレーム側に含まれる。
- `first_completed_ms`：プログラム開始から最初のフレームの処理完了。interop/合成は初回読み戻しQAも含む。純粋な実装比較用の初期化費用とは異なる。
- `completed_interval_ms`：一つ前のフレーム完了から当該完了まで。demux、packet送信、receive、GPU完了待ち、選択した受け渡し/合成、前フレームCSV書き込みを含む。各周30枚を除外した合計時間から定常fpsを計算する。
- p50/p95/p99：上記完了間隔のnearest-rankに近い離散分位（配列のceil(p*(n-1))番目）。個々の圧縮パケットの入力から表示までのlatencyではない。decoder先読みでburst出力があり得る。
- `receive_ms`：avcodec_receive_frame呼び出しのみ。単独のGPU処理時間ではない。
- `delivery_ms`：receive後のGPU完了待ち・download/upload/interop/合成。GPU timestamp queryによる内訳ではない。
- `seek_first_p95_ms`：先頭へのav_seek_frame、avcodec_flush_buffers後、最初の処理完了まで。毎回ファイル先頭へのseekであり、ランダム位置・逆方向へのseekを代表しない。

Vulkan modeでもAVVkFrameの全timeline semaphoreが指定値へ到達するまで待つ。GPU commandの投入回数をfpsと誤認しない。interopのcopyでも値を待機し、使用後に増分signalを行う。GPU待機とD3D11 event queryには10秒の上限がある。ただしFFmpeg内部の初回receiveで停止する場合はその外側のタイムアウトでは止められないため、Python supervisorが60秒でプロセスを終了する。正式baselineの停止例は旧supervisorの実行中に4分超の無進行を確認し、対象PIDだけを手動終了した。

CPU使用率はGetProcessTimesのuser+kernelを全論理CPU数とプロセス全体wall timeで正規化。定常区間だけのCPU使用率ではない。メモリはprocess peak working setと終了時private bytes。GPU使用率・memory.used・power.drawはnvidia-smiの200 ms間隔サンプルで、**GPU全体**の値。他アプリやdesktopを含み、プロセス専用GPU負荷/VRAM使用量ではない。短いCPU/Vulkan条件ではサンプル数が少ない。

## 受け渡しの実態

| モード | CPU画素経由 | GPUコピー/処理 |
|---|---|---|
| cpu | CPUデコード出力のみ | なし |
| vulkan | 非圧縮画素のCPU転送なし | FFmpeg内部decode compute、結果完了待ち |
| download | GPU→CPU | av_hwframe_transfer_data（内部copy/変換数は本計測器では未計測） |
| cpu-d3d11 | CPU→GPU | プレーンごとのUpdateSubresource。ドライバー内部copy数は不明 |
| download-d3d11 | GPU→CPU→GPU | downloadとUpdateSubresource |
| interop | 定常時の非圧縮画素はCPUを通らない | 各プレーンvkCmdCopyImage 1回 + D3D11 CopyResource 1回 |

interopはD3D11でR16_UNORM共有NTハンドル付きテクスチャを作り、VulkanへD3D11_TEXTURE handleとしてimportする。LUID一致、外部画像のIMPORTABLE、メモリ型の交差を確認する。各プレーンのKeyed MutexをVulkan key=0で取得しkey=1で解放、D3D11がkey=1で取得して通常テクスチャへcopyし、D3D11完了後key=0へ戻す。画像layout/queue familyのexternal ownership transferも行う。

FFmpegのAVFrameはcopy完了まで所有し、独自commandが使うtimeline値を増分更新する。frame/queue lockを用い、poolへ早期返却しない。今回の試作は同期待ちをホストで行うため、最適な非同期ring bufferではない。異なるGPU間や共有不可能なformatへ暗黙にfallbackしない。

「ゼロコピー」は全経路に成立しないため、本成果物では性能の説明に使用しない。共有メモリのimport自体は追加画素コピーを必要としないが、decode画像から共有画像、共有画像からconsumer画像には実際のcopy commandがある。圧縮入力のCPU→GPU送信やdecode内部の中間処理はこの2回に含まない。

初回のみ、interopのD3D11 consumer画像をstagingへ戻し、同じGPUフレームのFFmpeg downloadと全プレーン・全有効画素をmemcmpする。このQA読み戻しは初回時間に入り、定常統計からは除外される。これは**受け渡しの完全一致**であり、CPUデコーダーとの一致とは別。

## 合成と競合

`--layers 4` は同じ入力フレームをD3D11 pixel shaderでBT.709 limitedからRGBA16Fへ変換し、4回draw/alpha blendする負荷モデル。初回はCPU数式との289点比較（RGBA各成分、許容0.01）を行う。クロマはnearest、アルファはstraight扱い。一般の色変換品質やHDR対応とは主張しない。入力metadataがBT.709 limitedでなければ拒否する。

`stress.py` は複数プロセスで独立デコーダーと独立D3D11コンテキスト/合成を同時に実行し、同GPU上での競合を測る。単一コンポジターに複数の異なる入力を集約したアプリではない。初期化の開始差と終了時の負荷差があるため、単体値からの精密なスケーリング則は推定しない。

## 品質・終了処理

`quality.py` は色変換なし、CPU/GPUを同じ出力pixel formatとbit depthでraw化し、プレーンごとのmax abs、MAE、MSE、PSNR、差分画素数、SHA256を保存する。PSNRが無限（完全一致）の場合はJSON nullとexact=trueを記録。`--native` はGPU完了待ちありの独自計測器を使う。raw書き込みを含む計測器のfpsは性能評価に使わない。

通常decodeのEOS、先頭seek/flush、欠損/空/途中切断ファイル、終了コードとPTSを確認する。純粋DX11 pluginではFLUSH_START/STOPを伴うseek、EOS、PAUSED/PLAYING/NULL反復、4K 30分、起動100回、seek 1000回を追加検査した。HQの1080p→4K→1080p解像度caps変更も同一pipelineで確認した。device lost、色のみ・非対応プロファイルへの動的caps変更、逆方向seek、EOS中flush、実モニターの色は未検証。QoS/drop、表示ウィンドウ・fullscreen・scanout・VSyncには部分的な測定があるが、安定表示の合格ではない。
