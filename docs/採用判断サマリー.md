# DX11 ProRes採用判断サマリー（2026-09-24）

結論：**DX11 decoder側の採用ゲートは未達**。純粋DX11復号・D3D11Memory出力、画素精度、破損拒否は検証済み。3面リングをdecoderスレッドで回収する版は、通常QoS・Present(0)の実写4K60×10周交互4組でdecoder QoS欠落が全試行0/4800枚だったが、回収待ち最大値が旧版12.222ms→44.401msへ悪化して不合格。続く専用完了ワーカー版は単発10周4800/4800枚・decoder QoS欠落0枚と回帰を通過したが、独立ステージ交互比較は未実施で採用を保留する。詳細は[VLD非同期化](VLD非同期化.md)。OS/DWM未表示はdecoderなしの負荷対照でも起きるため、このdecoder側ゲートから外し参考値として別記する。Vulkan版へ切り替えていない。

RGB基準はBT.709 limited YUV、BT.709 matrix・transfer・primaries、水平中央クロマからfull-range RGB10A2への変換であり、最終10bit丸めの1 codeを数値許容差とした。素材のchroma locationは未指定なので、製品側のクロマ位置・許容値の合意は残る。GPU値とCPU `videoconvert` 値には丸め・実装の系統差もある。

測定環境はRTX 3070、GStreamer 1.28.2、60 Hz画面。CPU参照はリポジトリ内固定SDK `tools/ffmpeg-n8.1-latest-win64-lgpl-shared-8.1/bin/ffmpeg.exe`。公開素材の出所、色メタデータ、SHA256、比較範囲、再現コマンド、試行別ログは[実素材と表示検証](実素材と表示検証.md)を参照。主要集計は `results/proton-real-yuv.json`、`results/dji-real-4k-yuv.json`、`results/dji-real-4k60-yuv.json`、対応する `*-rgb-element-formula.json`／`dji-real-4k60-rgb-formula.json`、`results/d3d11-display-native-rgb-1080-summary.json`、`results/d3d11-display-native-rgb-4k-summary.json`、`results/presentmon-1080p60-qpc-summary.json`、`results/dji-real-4k60-display-summary.json`、`results/dji-real-4k60-etw-repeat-*.json`。回帰検査は `results/verification-reference-stress-dx11.log` と `results/verification-reference-stress-plugin.log` に保存済み。

Win32K tokenを追加した別の実写4K60・3試行では、同じくsinkは4320/4320枚、DXGI全4329件成功だが、PTS内側120/4302枚にOS表示時刻がなかった。DWM未消費129件のうち117件は次に消費されたtokenと0.1ms以内にInFrame、12件はRetired状態を経ない。消費済み隣接4065組では同時InFrameは0件。これは同一合成タイミングの置換を強く示唆するが、正確なキュー位置・原因を確定せず、`results/dji-real-4k60-token-2026-09-24/win32k-summary.json`に記録した。

同じETLのDxgKrnl PresentHistoryをWin32K tokenへ全4329件結合し、DWM未消費129件は全てDxgKrnl ready後にInFrameへ進んだと確認した。GPU ready以前の停滞では説明できないが、readyは実表示やDWM消費を保証しない。詳細は`results/dji-real-4k60-token-2026-09-24/dxgkrnl-present-history-summary.json`。

標準sinkに近い診断でPresent同期値だけを0→1へ変えた実写4K60の最前面3組は、OS未表示が382/4302→0/4302枚、最大OS表示間隔が約33.4→21.6msだった。一方、非最前面の2組では同期値0が107/8枚、1が0/5枚（各1434枚）と変動し、同期値1だけで全条件の無欠落とはならない。全試行のGStreamer出力は1440/1440枚、drop/QoS 0。毎フレームのCOM照会という計測交絡を除いた後の値だけを採用した。非公開ABIを差し替える検査手段は製品実装に使わない。条件・個別記録は[Present同期診断](Present同期診断.md)と`results/present-sync-standard-2026-09-24/`。

通常decoder QoSへ戻した同期値1・最前面の実写4K60・2試行では、OS内側未表示は各0枚でも、復号出力前に14・2枚がQoS破棄された。1試行の`Present1(1)` API最大110.327msと後続sink push最大119.2msが重なった。同期値0の単発対照は欠落0であり、試行間変動が大きく、この少数試行から同期値1の通常QoSへの優劣は断定しない。end-to-end無欠落と短い最大待ちの両立は未達。詳細は`results/present-sync-normal-qos-2026-09-24/`。

追加のWin32K時刻照合では、DWM未消費129件のうちRetiredあり117件は直後tokenの作成が自身のInFrameより先、Retiredなし12件は後だった。表示済み隣接4065組にも先行41組があり、それだけを原因とはしない。標準sinkの時計同期を外した診断は4K60でQoS欠落を各4→0枚へ減らした一方、24fps実写129枚を5,335→2,114msで再生し、素材PTSを失った。製品設定へは採用しない。詳細は[Present同期診断](Present同期診断.md)。

プラグインDLL・shader・説明を分離した内部検証ステージでは、比較用Vulkan DLLなしで両GStreamer要素のロード、1080p/4KのD3D11Memory復号とBT.709 RGB変換を完走した。直接依存にFFmpeg/Vulkan/D3DCompilerはなく、全11ファイルのSHA256を`results/stage-d3d11-internal-2026-09-24.json`へ記録した。これは外部配布の認定ではない。リポジトリの公開ライセンス・対応ソース、他GPU、実表示のゲートは引き続き未達。

ソフトウェアadapterをGPU復号と誤認しないようDXGI判定を追加した。WARPをGStreamer contextへ注入したdecoderと、WARP製D3D11Memoryを直接受けた専用RGB要素は、いずれも`RESOURCE/FAILED`で停止した。RTX 3070の回帰は通過した。他の物理GPUや実際のdevice lostを検証済みとはしない。

VLDエラーフラグのstaging Mapは`DO_NOT_WAIT`と10秒期限で待ち、device状態を確認するよう変更した。期限や失敗分岐は模擬HRESULTで単体検査し、実GPUの復号・EOS/seekと公開素材779枚で回帰した。変更前後の3反復中央値は1080p direct 321.793→322.318 fps、4K direct 146.484→144.752 fpsで、大きな定常性能低下は観測されなかった。実際のdevice lostやdriver内部の停止を試験したものではなく、互換性・表示ゲートは未達。記録は`results/verification-vld-map-timeout-2026-09-24/`。

CPU参照の決定的変異＋ASanで、AC runが係数面末尾の1つ先に達した際の逆スキャン表境界外参照を検出し、CPUとSM5 VLDの同一境界式を修正した。4素材・2,000変異のASan再検査は完走し、該当末尾到達9件を拒否。単一バイト再現例はGPUでも同じjobの`STREAM/DECODE`となり、合成画質と公開素材779枚の回帰を通過した。入力安全性全体や他GPUを保証する結果ではない。`results/verification-parser-mutation-2026-09-24/summary.json`、`results/verification-ac-boundary-2026-09-24/`。

修正後の単独性能測定には約7～16%の低い値があったため、旧版・新版の独立ステージを同じRTX 3070で交互4組比較した。正常な合成素材のdirect/download、1080p/4Kの4条件で、各4試行の旧→新中央値差は−0.661%、+0.387%、−0.183%、−0.665%。4K downloadには新版だけ89.891fpsの外れ値が1件あり、一般的な無回帰保証にはしない。大幅な低下が境界修正によって一貫して起こる証拠は得られなかった。`results/ac-boundary-ab-summary-2026-09-24.json`。

DX11版の対応ソースと専用CMake定義を含む内部ステージを作り、元リポジトリのビルド定義やFFmpeg/Vulkan SDKなしでDLL/CSOを再ビルドし、RGB D3D11Memoryまで実行した。`results/stage-d3d11-source-rebuild-2026-09-24.json`に20ファイルのSHA256と依存を記録。ソースを同梱できたことは公開ライセンスや提供条件の確定を意味しない。

RGB後の4 buffer queueを挟む交互2組の実写4K60診断でも、GStreamer各1440/1440枚・QoS 0の一方、OS表示時刻なしはqueueなし8・5枚、あり65・1枚で残った。sink時計同期は保ち、queueを製品経路へ採用しない。詳細は[実素材と表示検証](実素材と表示検証.md)。

標準sinkの公開`processing-deadline`を既定15msと45msで交互4組比較すると、実写4K60の各1440/1440枚は通常QoSで出力され、内側OS表示時刻なしは合計220/5736枚対29/5736枚だった。ただし45msでも3/4試行に未表示があり、最大OS表示間隔は約33msに達する。24fpsのPTS再生速度は短時間試行で維持したが、長時間・他GPUは未検証。45msを完成経路の既定値とはしない。詳細は[実素材と表示検証](実素材と表示検証.md)。

後続の非最前面2組では前面ウィンドウとの矩形重なり率が全Present行23%で一定でも、15msのOS未表示は1/1432・172/1434枚、45msは7/1434・80/1434枚と大きく変動した。多発した未表示はGPU完了前後の2群に分かれる。15msの1試行ではdecoder QoS欠落2枚も起きた。45msは非最前面の無欠落策ではなく、通常QoS・表示間隔の採用ゲートは未達。詳細は[実素材と表示検証](実素材と表示検証.md)。

10周/約80秒へ延長した非最前面の交互2組でも、15msはdecoder QoS欠落16・2枚、OS未表示18・179枚、45msはdecoder QoS欠落1・4枚、OS未表示223・85枚だった。15msの1試行には最大133msの表示間隔があり、45msも約33ms。窓状態と捕捉を揃えても未表示は周回に集中する。公開設定の処理期限だけではend-to-end無欠落と短い最大間隔を両立せず、製品採用は引き続き保留。詳細は[実素材と表示検証](実素材と表示検証.md)。

次は保守可能なsink側変更候補、非最前面・通常QoS・別素材・長時間の実表示を検証する。decoder QoS欠落、sink待ち、OS未表示を別々に減らし、実写4K60でend-to-end 0欠落と短い最大表示間隔を両立させる。その後に他GPU、device lost、多入力実表示を採用ゲートとして確認する。非対応形式への動的caps変更はエラー停止を検証済み。これらが済むまで最終目標の完了・製品採用とはしない。
